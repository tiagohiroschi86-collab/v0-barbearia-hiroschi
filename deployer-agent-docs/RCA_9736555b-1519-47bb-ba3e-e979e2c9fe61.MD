# RCA — build_image failure (run 9736555b-1519-47bb-ba3e-e979e2c9fe61)

## Deployment
- deployment: hiroschi-dev-preview (1d7860df-0ca5-4a6d-9d9a-5d79a122a39e)
- template: nextjs_mongo_shadcn_base_image (Next.js, kubernetes frontend, arm64, tier_0)
- failed step: **build_image** (frontend builder stage, `pnpm i --frozen-lockfile`)
- Same failure occurred on the prior run 6a7bc7dc-7b0a-4aaa-94f7-78f0a0c62e31 — reproducible, not flaky.

## Symptom
Build aborts during frontend dependency install:
```
success Installed "pnpm@12.14.0"
[RETRY] Attempt 1 of 3: pnpm i --frozen-lockfile
[WARN] The "pnpm" field in package.json is no longer read by pnpm.
       The following keys were ignored: "pnpm.onlyBuiltDependencies".
Error: ERR_PNPM_IGNORED_BUILDS
  × installing dependencies
  ╰─▶ Ignored build scripts: @firebase/util@1.15.1, protobufjs@7.6.2, sharp@0.34.5
  help: Run "pnpm approve-builds" to pick which dependencies should be allowed to run scripts.
[RETRY] All 3 attempts failed  → exit code 1
```

## Root cause (proven by the build log, not reproduced — eph sandbox failed to spawn, platform-side)
The frontend `package.json` carries a `pnpm.onlyBuiltDependencies` allowlist to permit the post-install build scripts of `sharp`, `@firebase/util`, and `protobufjs`. The build base image now ships **pnpm 12.14.0**, which **no longer reads the `pnpm` field from `package.json`** (the log says so verbatim) — the setting moved to `pnpm-workspace.yaml`. With no recognized allowlist, pnpm 12 does not silently skip those build scripts; it treats them as a hard error (`ERR_PNPM_IGNORED_BUILDS`) and fails the install. All three retries hit the same wall → `build_image` fails before an image is produced.

This is not a missing dependency, a lockfile mismatch, a secret, a tier, or a resource issue. It is a pnpm-config-location migration.

## Fix (Code — E1 applies, then redeploy)
Add a `pnpm-workspace.yaml` at the frontend project root (the directory containing the frontend `package.json`) with the build-script allowlist in its new home:

```yaml
onlyBuiltDependencies:
  - sharp
  - '@firebase/util'
  - protobufjs
```

Notes:
- This does **not** modify the lockfile, so `pnpm i --frozen-lockfile` stays valid.
- Equivalent to running `pnpm approve-builds` and selecting those three packages (that command writes this same file).
- The stale `pnpm.onlyBuiltDependencies` block in `package.json` can be left or removed; pnpm 12 ignores it either way.
- If a `pnpm-workspace.yaml` already exists, merge the `onlyBuiltDependencies` key into it rather than overwriting.

## Why not a manifest fix
The failing `pnpm i --frozen-lockfile` command lives in the platform Next.js template Dockerfile, not in app source. However this deployment has **no manifest override in GCS** and uses a **non-farm template**, so writing any manifest flips the build to load the complete set from GCS — a set I have no authoritative copy of for this template (the skill's reference manifests are farm-only, and fabricating the Dockerfile/nginx/entrypoint is prohibited and would fail at template load). The source-side `pnpm-workspace.yaml` is the correct, minimal, low-risk fix and resolves it at its true origin.

## Next action
